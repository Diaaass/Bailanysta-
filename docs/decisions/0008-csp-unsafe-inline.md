# 0008. CSP с `unsafe-inline` для скриптов

## Контекст

Заголовки безопасности добавлены, включая Content-Security-Policy. Строгая
политика запрещает инлайновые скрипты — это главное, что превращает XSS из
выполнения кода в безобидную вставку текста.

Next.js при этом отдаёт инлайновые `<script>`: данные гидратации и скрипт
темы, который выставляет класс до первой отрисовки, чтобы страница не мигала
светлой темой. Запретить инлайн, не сломав приложение, можно только через
nonce, выдаваемый на каждый запрос в `proxy.ts` и прокидываемый в каждый
инлайновый скрипт.

## Решение

`script-src 'self' 'unsafe-inline'`. Остальная политика строгая:
`default-src 'self'`, `object-src 'none'`, `frame-ancestors 'none'`,
`base-uri 'self'`, `form-action 'self'`. `unsafe-eval` добавляется только в
разработке — его требует HMR Turbopack.

## Последствия

**Хорошее.** Заголовки закрывают кликджекинг, MIME-sniffing, утечку реферера и
подмену `<base>`. `connect-src 'self'` означает, что страница ходит только на
свой домен — ключ AI и так вызывается с сервера, но теперь это ещё и запрещено
политикой.

**Плохое.** `unsafe-inline` ослабляет именно защиту от XSS. Смягчающее
обстоятельство: React экранирует вывод, `dangerouslySetInnerHTML` в проекте не
используется ни разу, а единственное место, где пользовательский ввод влияет на
навигацию — `callbackUrl` — санируется явно (см. `safeCallbackUrl`).

**Что заставило бы пересмотреть.** Появление любого приёма, вставляющего HTML
без экранирования, или работа с чужими персональными данными. Тогда nonce
перестаёт быть излишеством.
